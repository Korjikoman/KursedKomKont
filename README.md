# База kursed: PostgreSQL + Python

Два сервиса Docker Compose:

- `postgres` — PostgreSQL 17 с сохранением данных в именованном томе.
- `migrate` — Python 3.13. После готовности PostgreSQL применяет SQL и завершает
  работу с кодом `0`. Состояние `Exited (0)` для него нормально.

Исходные SQL написаны для PostgreSQL 12; здесь используется PostgreSQL 17.
База называется именно `kursed`: это проверяет исходный SQL-скрипт.
Python подключается к `postgres:5432` по внутренней сети Compose.

## Запуск

Из каталога проекта:

```bash
docker compose up -d --build
docker compose logs -f migrate
docker compose ps -a
```

Успешное окончание установки: в логах `SUCCESS: migrations committed; database is ready`,
контейнер `migrate` завершился с кодом `0`.
Готовность самого PostgreSQL ещё не означает завершение установки схемы.
Для проверки кода завершения:

```bash
docker compose wait migrate
```

Настройки по умолчанию уже работают. При необходимости скопируйте `.env.example`
в `.env` и измените порт или пароль **перед первым запуском**.
Изменение пароля в `.env` не меняет пароль внутри уже созданной базы.

## Подключение из DBeaver

| Параметр | Значение по умолчанию |
| --- | --- |
| Host | `localhost` |
| Port | `5433` |
| Database | `kursed` |
| Username | `kursed` |
| Password | `kursed_dev_password` |

Порт опубликован только на `127.0.0.1`. Если `5433` занят, задайте другой
`POSTGRES_PORT` в `.env`. Внутри сети Docker порт остаётся `5432`.

## Применение SQL

Порядок задан явно в `migrate.py`:

1. `kursed_postgresql12_dbeaver.sql` — 16 основных таблиц.
2. `komkont_triggers_12_functions.sql` — 5 дополнительных таблиц, функции и триггеры.

Исходные файлы подключены только для чтения и не изменяются.
Для этих двух файлов Python убирает их внешние `BEGIN;` / `COMMIT;` в памяти,
затем выполняет оба файла и запись истории в одной общей транзакции.
Ошибка откатывает весь текущий запуск. Скрипт не делит SQL по `;`, поэтому тела
PL/pgSQL-функций и блоки `DO` остаются целыми.

История и SHA-256 файлов хранятся в `migration_meta.schema_migrations`.
При повторном запуске применённые файлы пропускаются; изменение применённого
файла приводит к ошибке. Блокировка защищает от одновременного запуска мигратора.
Автоматическое присвоение истории существующей схеме не выполняется: для первого
запуска нужна база без объектов этой модели, как требует исходный SQL.

Повторно запустить мигратор, например после исправления ошибки:

```bash
docker compose up -d migrate
docker compose logs -f migrate
```

При изменении Python-кода или зависимостей добавьте `--build`.
Для дальнейшего развития схемы добавляйте новый SQL-файл в `SQL_FILES` и его
bind mount в `compose.yaml`. Новый файл должен иметь одну внешнюю пару
`BEGIN;` / `COMMIT;` на отдельных строках, как текущие файлы.
Сложные сценарии миграций удобнее вести через Liquibase или другой мигратор.

## Выполненная проверка

Конфигурация проверена командой `docker compose config --quiet`, синтаксис
Python проверен. На временной базе PostgreSQL 17 в однопользовательском режиме
проверены оба SQL-файла: созданы 21 таблица, 12 прикладных функций и 11 триггеров,
выполнены примеры вызовов функций. Намеренная ошибка после выполнения SQL
подтвердила откат всей установки.

Сборка образа, работа Python с драйвером и запуск двух контейнеров в этой сессии
не проверены: доступ к Docker-сокету запрещён, скачивание зависимостей из
локальной среды недоступно.

## Проверка базы

```bash
docker compose exec postgres psql -U kursed -d kursed -c '\dt public.*'
docker compose exec postgres psql -U kursed -d kursed -c 'TABLE migration_meta.schema_migrations;'
docker compose exec postgres psql -U kursed -d kursed -c 'SELECT * FROM public.kk_debtors();'
```

Ожидается 21 таблица в `public` и две записи истории. Тестовые студенты,
договоры и платежи не добавляются: устанавливаются структура и логика БД.

## Остановка

```bash
docker compose down
```

Данные сохраняются в томе. Команда `docker compose down -v` удаляет том
вместе со всеми данными; используйте её только для намеренного сброса базы.
